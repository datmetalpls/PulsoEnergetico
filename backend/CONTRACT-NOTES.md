# Decisiones mínimas para v0.1

- Sesión inicial: `running`, pausada, controles apagados y 0 Wh; representa «sin iniciar» sin añadir un tercer estado al contrato.
- Cierre: no existe ruta de cierre en §6. Crear un ensayo cierra el anterior tras ponerlo al día, congela sus valores y conserva su reporte. El respaldo crea sesiones ya cerradas sin tocar las activas.
- Importación: el primer `instant` importado de la sesión define `telemetry_origin` (t=0). No se compara contra la fecha real de creación; así el fixture histórico integra sus tres intervalos. El lote conserva el orden recibido y los valores negativos respecto del origen se clasifican como fuera de orden cuando hay referencia. Se pausa el simulador al importar para no mezclar relojes automáticamente.
- Respuesta de lecturas: lote totalmente duplicado devuelve `200 {"status":"duplicate"}`, excepción explícita a «todas las escrituras devuelven state»; lote con fuera de orden devuelve state y 202. No se añaden contadores al JSON de state.
- `GET /api/localities`: lista `[{slug,name,country,timezone,sites:[{slug,name,kind,fictitious,budget_kwh_day,sample_interval_s}]}]`, compatible con `LocalityWithSites[]` del frontend; el contrato no incluye un fixture para esa ruta.
- `on_seconds` del reporte es el máximo entre zonas (tiempo efectivo de la carga más utilizada), para no sumar segundos simultáneos como si fueran duración de ensayo. El detalle por zona está en state.
- `/advance` acepta segundos enteros y emite una última lectura parcial si el avance no cae sobre el muestreo; así procesa exactamente N segundos. Los ticks normales mantienen el muestreo de 1/60 segundos. Los cambios inmediatos usan sufijo determinista `:change:N` porque el id de una muestra programada en el mismo t no puede reutilizarse para otra potencia.
- Un corte explícito siempre crea Gap al reconectar, incluso si dura menos de tres muestras. Ocultar la pestaña no es un corte: el catch-up procesa hasta 3600 ticks reales por petición con escrituras en lote; conserva el tiempo restante para próximas peticiones, sin descartarlo ni crear gaps ficticios.
- «Siguiente franja» después de noche salta a las 08:00 del día siguiente; solo mueve scenario_offset_s. Velocidad de sede: 60 o 300; banco: 1.
- El presupuesto nuevo se aplica también a la sesión activa; no borra una alerta anterior. Los parámetros eléctricos se validan contra el voltaje y la corriente nominal/máxima de la zona.
- Auditoría: cada escritura API exitosa y comandos de carga registran AuditEvent; nunca se registran contraseñas. Los avances por polling son cambios internos bajo el bloqueo de la sesión.
- Docker exige Angular compilado: un fallo de `npm ci`, `npm run build` o la ausencia de `index.html` aborta el build. Compose lee `.env.example` y superpone `.env` si existe; el despliegue EC2 exige redefinir las seis credenciales privadas.
- Importación: hasta 5000 lecturas y un cuerpo JSON de hasta 2 MiB (incluye estructura, IDs y comentarios). Un lote ASCII de 5000 IDs de 200 caracteres cabe en ese límite; si los comentarios o el escape Unicode lo exceden, dividir el lote. Los errores de tamaño y JSON devuelven 400 JSON de validación. Los tiempos importados deben caber en ambos contadores de sesión de 32 bits; IDs con NUL son inválidos.
- El reporte de una sesión cerrada conserva energía y tiempos, pero su potencia actual es 0 W.

## Propuestas de cambio de contrato (pendientes de aprobación de Claude)

- **`zones[].setpoint_current_a` (aditivo, opcional, compatible hacia atrás):** cuando la carga DC del banco (`kind == "dc_load"`, p. ej. `carga-5v`) está apagada (`on: false`), `current_a` devuelve `0.0` (`power_w / voltage_v`) para preservar la identidad `power_w = voltage_v × current_a` de §1, pero la perilla de la UI quedaba mostrando `0,00 A` en lugar de la consigna guardada en `ZoneState.current_a`. Se propone añadir el campo opcional `setpoint_current_a` (`number | null`): refleja la consigna configurada (`ZoneState.current_a`, por defecto `0.4` A) en zonas `dc_load` incluso estando apagadas, y `null` en zonas `light` (análogo a `intensity_pct` en luces regulables y `max_current_a` en cargas DC). No elimina ni renombra campos existentes; clientes que lo ignoren siguen funcionando igual, y el frontend podrá enlazar la perilla a `zone.setpoint_current_a ?? zone.current_a`. Si Claude lo aprueba, corresponde reflejarlo en `docs/02-contrato.md` y `contracts/state*.example.json`.
- **Rate limiting en `POST /api/auth/login` (`429 {"error":"rate_limited"}` + cabecera `Retry-After`):** tras exceder `LOGIN_RATE_LIMIT` intentos fallidos (por defecto `5`) desde la misma IP (`REMOTE_ADDR`) dentro de `LOGIN_RATE_WINDOW_S` segundos (por defecto `60`), `POST /api/auth/login` responde `429 {"error":"rate_limited"}` con `Retry-After` antes de invocar `authenticate()`. Un login exitoso limpia el contador de esa IP para no interferir con la demo ni con `scripts/acceptance.py`. Si Claude lo aprueba, puede agregarse `429` a la línea de errores de §6 en `docs/02-contrato.md`.

## Integración con Discord (v0.1.2, aditivo)

- **Mecanismo:** webhook de canal (sin bot ni token). La URL se lee de `DISCORD_WEBHOOK_URL` (definida solo en `.env`, no versionado; `.env.example` la deja vacía). Nunca se serializa, se registra ni aparece en errores; los logs registran solo el código HTTP o el tipo de excepción. `energy/discord.py` usa `urllib` (sin dependencias nuevas), `timeout` de 5 s, `username` «Pulso Energético», `allowed_mentions` vacío y `avatar_url` solo si se define `DISCORD_AVATAR_URL`. Un `429` de Discord no se reintenta: se respeta su `Retry-After`.
- **Alerta:** al crearse la alerta de umbral (una por sesión) se envía un embed dorado con sitio, localidad, hora del escenario, energía acumulada y umbral (Wh en el banco, kWh con 2 decimales en la sede) y el pie «Datos simulados · Prototipo hackatón Ecuador × Chile». Se programa con `transaction.on_commit` y corre en un hilo aparte, así que nunca bloquea la petición ni provoca un 500. Cada intento registra `AuditEvent` «discord.alert» con `{ok, http_status}`. Idempotente: `Alert.discord_sent_at` (migración `0002_discord`) se fija solo tras un 2xx; si ya tiene fecha no se reenvía. Un fallo no reintenta.
- **Reporte manual:** `POST /api/sessions/{id}/discord/report` (operador del sitio, CSRF; también en sesiones cerradas) envía un embed petróleo con el texto del reporte. 1 envío cada 30 s por sesión (cuenta cada intento, también fallidos): `429 {"error":"rate_limited"}` + `Retry-After`. Sin webhook: `409 {"error":"discord_not_configured"}`. Fallo de red o HTTP de Discord: `502 {"error":"discord_unavailable"}` (o `429` si Discord limitó). Éxito: `200` con el reporte. Cada intento registra `AuditEvent` «discord.report» con `{ok, http_status}`. `Session.discord_report_sent_at` guarda el último envío correcto.
- **Campos nuevos:** `state.discord = {configured, last_sent_at, alert_sent, report_sent, sent, label}`; `report.discord = {configured, last_sent_at, alert_sent, report_sent}`; `alerts[].discord_sent_at`. `discord_preview.sent` es `true` cuando se envió algo de la sesión; `label` vale «Enviado a Discord» (alerta o reporte enviados), «Discord configurado» (hay webhook y aún no se envió nada) o «Simulación local» (sin webhook). En producción el envío de la alerta es asíncrono: la respuesta que crea la alerta aún dice «Discord configurado» y el siguiente poll muestra «Enviado a Discord».
- **Pruebas:** bajo `manage.py test` se ignora `DISCORD_WEBHOOK_URL` (solo cuenta `DISCORD_WEBHOOK_URL_TEST`, que las pruebas fijan con un dominio `.invalid`) y `urlopen` está mockeado; ninguna prueba toca la red.
